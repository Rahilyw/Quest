# Build 3: from launch pack to the pilot's growth engine (Nov 25, 2026)

Builds 1 and 2 finished the pilot's code and are proving its backend. Build 3 covers almost everything
left on the [roadmap](../../ROADMAP.md) and the specs. It runs in four waves:

- **Wave 0:** close build 2.
- **Wave 1:** the launch pack the first TestFlight build and Apple review need.
- **Wave 2:** the retention features the pilot cohort gets over the air during R1.
- **Wave 3:** the data-gated features that wait on pilot numbers.

The work is split across several kinds of coding agent at once: Claude Code (coordinator, subagents,
the feature pipeline, Workflow reviews), Cursor (Agent mode and background agents) and the owner.
Section 3 says who does what, and section 5 is the file-ownership contract that keeps them from
colliding.

The status words are the same as before, used strictly: **in checkout**, **locally tested**,
**applied**, **deployed**, **device-verified**.

## 3. Who does what

Each tool gets the work it's best at. No two of them edit the same file at the same time.

| Role | Tool | Does | Never does |
|---|---|---|---|
| **Coordinator** | Claude Code in the main checkout | Cuts the integration branch. Hands out cards and keeps the status table current. Merges card branches with `--no-ff` once CI is green. Owns `BUILD-3-LOG.md`, the ledger, `lib/analytics.ts` after N0, and the migration-number registry (§6). Runs the review workflows. | Builds cards itself while other agents are running, or touches any hosted service. |
| **SQL and server builder** | The Claude Code feature pipeline (`planner` → `coder` → `tester` → `reviewer`), one card per git worktree | Cards whose weight is migrations, pgTAP and edge functions: N1, N3, N4, G1, G2. Each pipeline run gets its own worktree (`isolation: "worktree"`), because `.pipeline/` is per checkout. | Mobile screens outside its card's file list. |
| **UI builder** | Cursor Agent mode, one chat per card; Cursor background agents for cards in the same wave | Screens, components and admin pages: K4, K5, N2, G3, G4, G6, plus the mobile halves of N1 and N3 when the coordinator splits them. | SQL in files 002–045 or the baseline. |
| **Doc and audit agent** | A Claude Code subagent (`general-purpose`, or `Explore` for read-only sweeps) | K1, K2 and K3. Read-heavy, write-light docs work. | App code. |
| **Independent reviewer** | A Claude Code Workflow with up to 4 agents, or a fresh Cursor chat as the fallback | Z (the security review). A pre-merge review of every wave. Each runs without the build history, so it reviews the code as written. | Fixes. Findings go back to the card's builder. |
| **Owner** | You | Everything hosted: `db push`, Vault, function deploys, webhooks, Vercel, EAS build, submit and update, Apple and Google accounts, vendor keys, content, gate readings. Merges PRs into `main`. | |

### How a card moves

```
coordinator hands out card ──► builder cuts its branch from the integration head
        ▲                              │ builds inside its file list
        │                              ▼
        │                     local gates (§8) → push → CI green
        │                              │
        └── coordinator merges --no-ff ◄┘  appends a log row, updates the status table
```

- Branches: `cursor/b3-<card>` for Cursor, `claude/b3-<card>` for Claude Code. Both patterns
  already trigger CI and the db-local job.
- Integration branch: `cursor/build-3`. Only the coordinator merges into it or pushes it.
- When a builder finishes, it reports four things: the commit SHA, the gate output, the files it
  touched, and any findings. A builder never merges its own card.

### Why duo merges at the start of Wave 2

N1 and N2 change mobile screens that duo also changes. Building them on top of duo avoids a
three-way merge later. Merging duo's code early is safe only if duo's UI is dark until 045 is
applied. **M5 must add that guard:** duo screens and queries are skipped when `min_party_size`
isn't in the schema. Without it, an over-the-air update would break the app on a database
without 045. If M5 can't add the guard, duo stays on its own branch and N1 and N2 avoid duo's
files.

## 8. Gates and stop conditions

Run these on every card branch, and again on `cursor/build-3` after each merge:

```
npm test --workspace @quest/geofence --ignore-scripts
npm test --workspace mobile --ignore-scripts
cd apps/mobile && npx tsc --noEmit && npm run lint:tokens -- --strict
cd apps/admin && npx tsc --noEmit && npx next build      # CI placeholder env vars
CI: db-local (apply, verify, pgTAP, db-types drift) and the deno job are green
```

These invariants carry over from builds 1 and 2:

- the mobile test count and the pgTAP assertion count never go down;
- raw tokens stay at 0;
- every new table has RLS and a pgTAP privacy test;
- every new client-readable column has its grant;
- every new migration has a `supabase/verify/0xx.sql` and a "Verifying 0xx" block in the README.

**Stop and report when:**

1. a gate or CI still fails after two honest fix attempts;
2. a card needs a file outside its §5 row, or a migration number not in §6;
3. a card needs to edit 002–040 or the baseline, or an applied migration from 041 on;
4. a step needs a hosted service: SQL there, a deploy, `link`, `db push`, EAS, Vercel, or any
   Supabase or Vercel MCP call;
5. a gate for a Wave 3 card can't be read from `/pilot` or PostHog;
6. two cards turn out to need the same file. The coordinator re-splits them; neither builder
   decides.
